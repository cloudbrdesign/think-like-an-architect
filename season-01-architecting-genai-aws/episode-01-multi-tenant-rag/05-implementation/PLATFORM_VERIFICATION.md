# Platform Verification — Veltamere Document Assistant

**Stage:** build authorisation and implementation design (E3) · **Date:** 2026-09-14

The architecture is approved. The AWS service mapping is a **candidate**, and this document records what has been
proven about it. It separates evidence that exists only in documentation from evidence that needs a real AWS account.

**Status in one line:** every load-bearing capability has been checked against current public documentation, and the
capability spikes have now been **run in a real sandbox account** (us-east-1, 2026-09-14). The results are in section 4
and the matrix in section 2. Evidence is recorded with account identifiers removed.

Verification classes used:
- **VERIFIED IN PUBLIC DOCUMENTATION** — AWS documentation states it, read on the date shown.
- **VERIFIED IN REAL AWS ACCOUNT** — observed in an experiment, with evidence.
- **NOT VERIFIED** — neither yet.
- **FALSE — MAPPING MUST CHANGE** — shown not to hold.

## 4. Capability spike plan

Spikes answer risky platform questions **before** the learner implementation is built. They are **verification
evidence, not the learner implementation**. Their code lives separately (`05-implementation/spikes/` at E4 time), uses
synthetic data only, and is destroyed after each run. A failed spike is useful evidence and is recorded, not hidden.

**Shared rules:**
- The sandbox, region and budget come from section 1.
- Every resource is tagged. As run, the spikes used the CloudBrewery lab tag standard (`Course`, `Season`, `Episode`,
  `Variant=spike`, `Purpose=verification`, …) rather than the `tla:*` keys drafted here; E4 aligns the implementation
  design's tags to that standard.
- Each spike ends with cleanup and a tag search.
- Result status is PASS / FAIL / INCONCLUSIVE.
- Evidence is command output with account identifiers redacted.

**Execution order:** I → F → C → A → B → E → G → D. Spike I creates the minimal stack the others reuse.

**Deployment identity findings.** These apply only when you deploy with a least-privilege deployment role rather than
an administrator. Neither is an architecture or service-mapping change:
- **Role lookup before creation.** CloudFormation looks up an IAM role by its bare name before creating it. For a role
  that does not exist yet, IAM authorises that lookup against `role/<name>` without the path. A deployment role limited
  to a role path therefore also needs read-only `iam:GetRole` on the bare-name pattern.
- **Stage tagging: an API Gateway authorization inconsistency.**
  - **Published reference:** AWS's service-action reference does not list `apigateway:TagResource`, and IAM Access
    Analyzer reports it as an invalid action.
  - **Observed in real execution:** `CreateStage` requests that contain tags are denied unless the deployment
    principal holds that action. A stage created without tags succeeds, and tagging an existing stage works with the
    documented permissions.
  - **Why it matters here:** CloudFormation always supplies its own stack tags when it creates a stage. The spike first
    added the action, a correction then removed it because the reference does not list it, and stage creation failed
    again.
  - **Consequence:** the TLA deployment role retains a narrowly scoped `apigateway:TagResource` compatibility permission
    for HTTP APIs in us-east-1. It is a deployment-plane permission only, supported by direct execution evidence, and
    revalidated periodically. It is not granted to any application runtime role.
- **Rollback clean-up.** If a stack fails before a role exists, the rollback clean-up of that role can be denied. Delete
  the stack again, retaining the never-created role.

**Estimated spike cost:** well under USD 1 in total — a few thousand tokens, tens of vectors, fewer than 500 requests.
There are no hourly-billed resources.
